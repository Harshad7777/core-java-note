### Q12. Explain your project.

My main project is the **Restaurant Management System (RMS)**, a web-based application designed to simplify and manage the daily operations of a restaurant.

- **Objective:** To eliminate manual paperwork, reduce billing errors, and manage restaurant activities efficiently through a centralized system.
- **Key Modules:** User authentication, category management, menu management, customer management, order management, kitchen order tracking, billing, dashboard, and sales reports.
- **Architecture:** Developed the backend using **Java and Spring Boot**, used **Spring JDBC (`JdbcTemplate`)** for database operations, and **MySQL** to store application data. The frontend is built using HTML, CSS, JavaScript, and JSP, communicating via **RESTful APIs**.
- **Security & Quality:** Implemented role-based access control (`ADMIN`, `STAFF`, `CHEF`) with **JWT-based authentication**, and tested and documented all APIs using **Postman** and **Swagger**.

This project gave me comprehensive experience in full-stack architecture, relational database management, API security, and debugging.

---

### Q13. Why did you choose this project?

Restaurants manage multiple interdependent activities simultaneously: updating menus, taking orders, tracking food preparation in the kitchen, and generating accurate bills.

Handling these operations manually often leads to miscommunication, delayed orders, billing discrepancies, and difficult record-keeping.

I wanted to develop a centralized application that streamlines these operations, reduces human error, and demonstrates my practical ability to build complete full-stack systems using Java, Spring Boot, Spring JDBC, and MySQL.

### Q14. What problem does your project solve?

The Restaurant Management System provides a unified, centralized platform:
1. **Reduces Manual Errors:** Replaces handwritten kitchen order tickets (KOT) with digital status tracking.
2. **Streamlines Billing:** Automatically calculates item subtotals, configurable taxes (GST), and discounts.
3. **Data Centralization:** Maintains a single source of truth for menu pricing, order history, and customer details.
4. **Role Separation:** Enforces security so administrators, waitstaff, and chefs only access functions relevant to their duties.

### Q17. What challenges did you face, and how did you resolve them?

**Challenge: Data Consistency Across Orders, Kitchen, and Billing**  
An order involves multiple related items. If an item was unavailable or a network glitch occurred mid-operation, partial order data could get recorded, resulting in incorrect kitchen tickets and billing discrepancies.

**How I resolved it:**
1. **Transaction Management:** Wrapped multi-step database writes in `@Transactional` blocks to ensure ACID compliance—either the full order is created or all changes are rolled back.
2. **Request Validation:** Added strict server-side validation to check menu item availability, quantities, and valid IDs before running SQL queries.
3. **Structured Debugging:** Inspected SQL queries in logs and tested boundary values using Postman to confirm data integrity.

## 10. Important Technical Rapid-Fire Preparation

Be prepared to answer these core technical questions in 2–4 concise sentences:

| # | Topic | Key Answer Summary |
| :-: | :--- | :--- |
| **1** | **JDK vs JRE vs JVM** | **JVM** executes bytecode. **JRE** = JVM + core libraries (runs apps). **JDK** = JRE + development tools (javac, debugger) used to build apps. |
| **2** | **OOP Concepts** | **Encapsulation** (data hiding with private fields & getters/setters), **Inheritance** (code reuse via `extends`), **Polymorphism** (overloading/overriding), **Abstraction** (hiding implementation via interfaces/abstract classes). |
| **3** | `==` vs `.equals()` | `==` compares memory references (addresses), while `.equals()` compares actual content/value of objects. |
| **4** | **Abstract Class vs Interface** | Abstract classes can have state (instance variables) and constructors; interfaces define contracts (all methods default public/abstract; support multiple inheritance). |
| **5** | **Exception Handling** | Handled using `try-catch-finally` or `throws`. Checked exceptions are verified at compile time; unchecked exceptions (`RuntimeException`) occur at runtime. |
| **6** | `ArrayList` vs `LinkedList` | `ArrayList` is backed by a dynamic array (faster $O(1)$ random access). `LinkedList` is backed by doubly-linked nodes (faster insertions/deletions). |
| **7** | **Spring Boot** | An opinionated extension of Spring that eliminates boilerplate XML configuration through auto-configuration, embedded servers (Tomcat), and starter dependencies. |
| **8** | **Dependency Injection & Autowiring** | **DI** is a design pattern where object dependencies are injected by the IoC container instead of created manually. `@Autowired` injects beans automatically by type. |
| **9** | **Spring MVC vs Spring Boot** | **Spring MVC** is a web framework based on Model-View-Controller. **Spring Boot** is a packaging and configuration utility that bundles Spring MVC with embedded servers and auto-configuration. |
| **10** | **JDBC & MySQL Connection** | JDBC connects Java to MySQL in 5 steps: load driver → establish connection (`DriverManager`) → create statement → execute query → process result set & close. |
| **11** | **REST API Methods** | **GET** (retrieve data), **POST** (create new resource), **PUT** (update existing resource completely), **DELETE** (remove resource). |
| **12** | `INNER JOIN` vs `LEFT JOIN` | `INNER JOIN` returns only matching rows from both tables. `LEFT JOIN` returns all rows from the left table and matched rows from the right table (NULL if no match). |
| **13** | **Primary Key, Foreign Key & Normalization** | **Primary Key** uniquely identifies a record. **Foreign Key** enforces referential integrity between tables. **Normalization** organizes tables to minimize data redundancy. |
| **14** | **Connecting Full Stack Flow** | Frontend sends an HTTP request (via Fetch/Axios) → Spring Boot Controller receives it → Service executes business logic → Repository/JDBC queries MySQL → Response sent back as JSON. |
| **15** | **API Testing with Postman/Swagger** | Postman sends test HTTP requests (Headers, Body, Params) to verify status codes (200, 201, 400, 404) and JSON responses. Swagger provides interactive documentation directly in the browser. |
